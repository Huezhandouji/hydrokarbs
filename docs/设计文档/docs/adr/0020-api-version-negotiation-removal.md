# ADR-0020:API 版本协商机制退场——API_VERSION 常量与 requiredApiVersion 声明删除

- 状态:已接受(2026-11-06;经 [32-v1.14修正案](../../32-v1.14修正案-API版本协商机制退场.md) 落盘为正式修正案)
- 关联:[32-v1.14修正案-API版本协商机制退场.md](../../32-v1.14修正案-API版本协商机制退场.md)(本裁决的变更指示与落盘凭据)、[ADR-0007](0007-standalone-framework-plugin-split.md)(★v1.1-D7 版本协商的引入处——本裁决整体退场)、[ADR-0013](0013-capability-tags-removal.md)/[ADR-0019](0019-shipped-limbo-mode-and-fallback-single-channel.md)(「删公共面成员 = 破坏性变更 + 用户裁决豁免双轨」先例)
- 验收:本次验收 = `gradlew build` 绿 + `publishToMavenLocal` 后 examples/TheirPlugin 独立 `build` 绿 + `grep -rn "API_VERSION\|requiredApiVersion" src/ examples/` 零命中;冻结测试处置见 32 号 §5(★19 FROZEN 17 行零改动、★44 BASELINE 删 2 行合法重录);★46 就地废止、★70 新增(计数 69→70,废止行不计有效命题)

## 背景

★v1.1-D7 引入的版本协商机制由三件组成:API 面常量 `MiniGameApi.API_VERSION`(1~8 只增不减)、SPI 声明 `MatchModeProvider#requiredApiVersion()`(默认 1)、消费方 `onEnable` 首行对照检查(`api == null || api.API_VERSION < REQUIRED` → SEVERE + `setEnabled(false)`)。用户裁决该机制退场,原话:「在 api 里面写一个表明 api 版本的字段毫无意义」。

机制检视(32 号 §1-D1 的完整论证):

1. **协商闭环自我比较**:三方(消费方 REQUIRED 常量、API 面常量、工厂声明)同源——同一框架 jar、同一版本链文档。恰好实现了检查的消费方必然刚按当前面重编译过(对照恒真);没重编译的旧编译物恰恰是版本检查拦不住的那批——它们内联读的还是旧常量值,真正的崩点(引用已删成员的 `NoSuchMethodError`)发生在检查之后的调用路径上。
2. **真实破坏性不经过版本数字**:历次破坏(★v1.4/★v1.6/★v1.7 删方法、★v1.13 删快照分量)全部发生在签名侧,由冻结测试(★19/★44 只增不改)与修正案流程把关;版本数字只做事后陈述,不提供拦截力。
3. **SPI 声明无对照面**:常量删除后 `requiredApiVersion()` 的唯一消费是注册日志一行,纯装饰;留壳即留死词汇(同 ★v1.13 否决「保留字段恒值」推理形状)。

## 决策

1. **机制四处一体退场**(不留半套):`MiniGameApi.API_VERSION` 常量、`MatchModeProvider#requiredApiVersion()` 默认方法(SPI 面收敛为 `id`/`build` 两法)、框架 `onEnable` 版本输出行、`registerMode` 注册日志的版本字段(保留 id 行——归属簿记与查重诊断仍需)。消费方首行检查收敛为**纯在场检查**(`api == null` → SEVERE + `setEnabled(false)`,拒载不崩服语义保留——框架插件缺席/加载失败仍是真实部署事故)。
2. **按破坏性变更口径处理,经用户裁决不设双轨**(第 5 次,同 ★v1.4/★v1.6/★v1.7/★v1.13 先例):删公共常量与删 SPI 公开默认方法 = 跨 jar 破坏(覆写过 `requiredApiVersion()` 的第三方需重编译)。方法面零变化:17 方法签名一字不动,★19 FROZEN 17 行不动;★44 BASELINE 删 2 行合法重录(背书 = 32 号/ADR-0020)。
3. **版本数字轴(1~8)随之终结,不再升版**:v1.0~v1.13 的 API_VERSION 沿革转为 CONTEXT「历史术语」表的历史陈述,新代码禁用;兼容性陈述改由版本链文档(README/AGENTS §3)+ 冻结测试 + maven 坐标承载。后续破坏性变更的公告载体 = 修正案 + ADR,不再有运行期数字锚点。
4. **验收处置**:★46(版本协商真值表)就地废止(编号不删不重排,先例 = ★32/★v1.7);★41 就地注(D7 打点增款退场,跨 jar 注册命题本体不变);★67 就地注(`API_VERSION = 8` 子句转历史陈述);新增 ★70(退场机械自证:全库零命中 + 重录基线 + 消费方在场检查)。14.36 条目就地废止(编号空置不复用)。

## 替代方案(已否)

- **仅删常量、保留 `requiredApiVersion()`(最小破坏)**:**否**——常量删除后声明值无对照面,只剩注册日志一行装饰消费;冻结面留死词汇,与「清除」冲突,且 SPI 面多一个无语义方法(用户已裁决整套退场)。
- **保留常量、删除检查仪式(反向最小破坏)**:**否**——常量在 API 面内部纯属冗余自曝(本 ADR 背景第 1 条),删除检查不改变其冗余性。
- **改为构建期版本断言(消费方 CI 对照 maven 坐标)**:**否,现阶段**——形态 A(单 jar)无真实跨 jar 消费者;形态 B 触发时若出现真实需求再裁(32 §6-Q1 候选解),不预先造机制件(同 21-D1「零消费者机制件删除」推理形状)。
- **`API_VERSION` 降为 `@Deprecated` 一个发布周期再删**:**否**——用户裁决豁免双轨(第 5 次),且本工程无对外发布节奏约束,过渡期只增加两套口径并存的窗口。

## 权衡

- **得**:①公共面少一个无语义常量与一个无语义 SPI 方法(「同一能力只留一份口径」——版本陈述只在文档层,不再三处冗余);②SPI 面回到 `id`/`build` 两法最小形状,与「注册工厂不是注册成品」语义贴合;③消费方接入仪式更短(在场检查一行);④兼容性责任归位——文档 + 坐标 + 冻结测试本就是版本轴的真实执行载体。
- **失**:①引用已删成员的旧编译物在运行期抛 `NoSuchFieldError`/`NoSuchMethodError`,不再有首行检查这道仪式性拦截(该拦截本就无效,见背景第 1 条;当前零真实第三方消费者,风险为假想面);②`API_VERSION` 数字轴终结后,「面向哪个面编译」只能查文档,少一个运行期可打印的数字(诊断场景改看 jar 版本/maven 坐标)。
- **先例分化**:历次破坏性变更「升 API_VERSION」的口径不适用本次——升版对象本身被删;后续破坏性变更不再有版本常量可升,以修正案 + ADR 为唯一公告载体(本 ADR 决策 3)。

## 后果

- 正:`MiniGameApi` 无 `API_VERSION` 常量;`MatchModeProvider` = `id`/`build` 两法;框架启动无版本行、注册日志只打 id;消费方首行 = 在场检查;★44 BASELINE 重录(删 2 行);★70 新增、★46 废止(计数 69→70 条,★46 废止行不计有效命题);14.36 废止(编号空置)。
- 负:旧编译物引用已删成员需重编译(examples/TheirPlugin 已随 v1.14 窗口同步);`TheirPluginGuardsTest` ★46 真值表用例删除(修测理由 = 32 号 §1-D5)。
