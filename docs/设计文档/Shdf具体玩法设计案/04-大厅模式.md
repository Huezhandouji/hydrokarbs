### 4.1 设计定位:大厅为什么不再是模式

v1.0 的论证是"大厅与竞技模式同构,所以大厅也做成一个 MatchMode"。v2.0 推翻的是**承载方式**,同构洞察本身保留(竞技模式之间仍互相同构):

| 维度 | v1.0(废止):大厅 = 框架模式 | v2.0(现行):大厅 = 主世界区域 + 宿主自管 |
|---|---|---|
| 位置 | 专属世界副本(`maps/lobby_main.yml`,tags `[lobby]`) | **服务器主世界**的一块固定区域(宿主 `config.yml` 的 `lobby:` 块声明) |
| 承载 | `MatchMode` 聚合根 + 会话实例 + 世界副本 | 宿主普通 Bukkit 代码;**不建会话、不注册模式、不占世界副本** |
| 职责 | 等人/投票/倒计时/闲玩(phases/vote/idle 组件表) | 暂定只有**模式投票 + 准备**(ready);闲玩/战报墙等留待宿主侧将来扩展 |
| 开局 | EndGate 倒计时到点 → `NEXT` + intent → `switchMode` | 大厅**开局判定**通过 → 宿主 `createSession` + `joinSession` 把对局托管给框架(§4.3) |
| 结束回大厅 | 竞技模式 `defaultTransition=FALLBACK` 切回 lobby 模式 | 对局散场 → 解散/离场 → 玩家回主世界 → 宿主接引至大厅(§4.6) |
| 常驻成本 | 大厅永远占一个会话实例与一个世界副本(rotation 硬撑) | 大厅常驻零切换;框架只在真正开局时介入 |

三条决策理由:

1. **资源模型错位**:大厅常驻、全员可见、活在主世界生态里(原生实体、其它插件、经济系统);对局是隔离副本、按场生灭。把常驻大厅塞进"按场生灭的会话"是 v1.0 的结构性别扭。
2. **"框架对大厅零感知"反而变成构造性成立**:ADR-0001"引擎里没有一行检查大厅"在 v2.0 下不需要靠测试守护——SHDF 的大厅根本不进框架词汇表(★13 的框架命题不受影响;本线不再以 lobby 模式落地,验收口径变化见 §4.8)。
3. **解散接引天然同向**:框架解散把名册成员传**主世界出生点**(hubRelocator,../15 适配层);大厅就在主世界——"框架送回家"与"宿主接回大厅"同向,只差一段宿主传送(§4.6)。

边界(大厅**不是**什么):

- **不是会话**:大厅成员不经框架名册;断线宽限、空场解散等会话机制不适用——掉线重进大厅是宿主自己的逻辑(§4.2)。
- **不是模式**:不注册 `MatchMode`、永不成为 `switchMode` 目标;"回大厅"在框架侧没有对应动词,只有"解散/离场后玩家在主世界"(§4.4/§4.6)。
- **不管对局内的一切**:队伍/计分/角色/表现照旧归框架会话;大厅只管"开局的入口"与"散场的出口"。

### 4.2 大厅的构成(宿主侧,全部普通 Bukkit 代码)

大厅无框架组件可用(它不在任何实例里)——这是特性不是缺陷:大厅逻辑不碰副本世界、不碰实例事件总线,普通监听器 + 自持状态即可,天然离线可测。

```java
package com.shdf.lobby;   // 宿主包根 com.shdf.*;与 mode/、bridge/ 平级的 lobby/ 包

/**
 * 主世界大厅管理器(宿主自管,v2.0):区域判定 + 成员账本 + 投票 + 准备 + 开局判定。
 * ★ 不是框架组件、不经会话——对框架的全部接触面是 MiniGameApi(§4.3)与事件订阅(§4.6)。
 * 职责暂定:模式投票 + 准备(本行随设计演进重读)。
 */
public final class LobbyManager {

    private final LobbyConfig cfg;            // config.yml lobby 块:bounds/spawn/vote-seconds/min-players...
    private final Set<UUID> present = new HashSet<>();   // 在大厅者(区域判定/进入按钮,主线程维护)
    private final Map<UUID, Boolean> ready = new HashMap<>();   // 准备账本
    private LobbyVote vote;                   // 当前一轮投票(无则空窗)
    private final MatchBootstrap bootstrap;    // 开局判定与 API 托管(§4.3)

    /** 进入大厅:主世界进入 lobby.bounds 区域(PlayerMoveEvent 节流判定)或 /shdf lobby 命令。 */
    public void enter(Player p) { /* 记账 + 传送 spawn + 发投票板 */ }
    /** 离开大厅:出界/进对局(§4.3 join 成功后)/退服。 */
    public void leave(UUID uuid) { present.remove(uuid); ready.remove(uuid); }
}
```

**投票(宿主版 `LobbyVote`)**:语义沿用 v1.0 `VoteComponent` 的裁决口径,但实现是宿主普通代码(聊天点击/箱子 GUI 任选;玩家名一律 `Placeholder.unparsed`,§14.10):

| 事项 | 口径(自 v1.0 VoteComponent 迁移) |
|---|---|
| 候选集 | `mode@map` 对;来源 = 宿主扫描 `games/*/`(玩法 id × 该玩法 maps 目录),空投给全量 |
| 计票 | 多数胜;平局 `TieBreak.RANDOM`(可配 `FIRST_LISTED`);每人一票、可改票 |
| 零票兜底 | rotation 轮换序取下一项(`games/rotation.yml`);轮换也空 → 本轮不开局,重新起票 |
| 周期 | `vote-seconds` 到点收票;全员 ready 可提前收票(快速开局) |
| 结果消费者 | 不是 `TransitionIntent`——是宿主 `MatchBootstrap`(§4.3)的入参 |

**准备(ready)**:`/shdf ready` 或 GUI 按钮;全员 ready 视为"立即开局"信号(人数门槛仍要过)。这是 v1.0"Gathering→Countdown"等待语义的宿主化:不再有 Countdown 阶段,判定通过即开局。

### 4.3 开局判定与 API 托管(MatchBootstrap)

大厅判定"可以开启对局"后,后续流程全部调 `MiniGameApi`(冻结面,../07 §7.1)托管给框架:

**开局门(全部通过才开)**:

| 门 | 判据 | 不过怎么办 |
|---|---|---|
| 人数 | 参与者(在场 + ready 群体)≥ 该玩法 `game.yml` 的 `min-players` | 继续等/重新起票 |
| 票选结果 | `LobbyVote` 已收票(winner 或 rotation 兜底) | 继续等 |
| 地图就绪 | 目标 map 已注册(`api.maps()` 含之);世界目录落盘在启动/重载时已保证(§4.5) | 摘除候选重收票 |
| 模式就绪 | 目标 mode 已注册(`api.mode(id)` 在场;宿主 onEnable 时已 `registerMode` 全量注册) | 属装配事故,SEVERE |
| 角色在场(按玩法) | 需要角色的玩法:`RoleFacade` 能 load 到 RoleAPI(§4.7) | 摘除该玩法候选,提示玩家;大厅照常 |

**托管时序(宿主 → 框架,一次开局)**:

```
 1  SessionInfo info = api.createSession(SessionRecipe.of(vote.modeId(), vote.mapId()));
    └─ 首模式 = 票选玩法,钉图 = 票选地图;extraComponents 按玩法会话流程装配(§4.4)
 2  for (UUID u : participants) {
        JoinResult r = api.joinSession(info.sessionId(), u);
        if (r instanceof JoinResult.Rejected rej) { /* 退票该玩家:留大厅 + 提示 rej.detail() */ }
    }
 3  lobby.leave(u)(join 成功者)—— 大厅账本移除;成员此后的生灭归框架名册
 4  对局进行 —— 框架托管(模式实例/组件/副本世界);大厅同时可服务下一轮投票(多会话并行自然成立)
```

```java
package com.shdf.lobby;

/** 开局判定 + API 托管(v2.0 新增)。唯一允许调 createSession 的地方——开局单闸。 */
final class MatchBootstrap {

    private final MiniGameApi api;
    private final GameConfigs games;          // games/*/ 自解析结果(§4.5)

    /** 开局(主线程;判定门全过才可进本方法)。失败路径全部人读可恢复:会话不建、玩家不挪。 */
    void openMatch(LobbyVote.Result result, Collection<UUID> participants) {
        GameConfig game = games.of(result.modeId());
        SessionRecipe recipe = new SessionRecipe(game.id(), Optional.of(result.mapId()),
                List.of(), game.sessionFlow().recipeExtras());   // §4.4:arena 挂散场引导+空场收尾;rotation 挂续局
        SessionInfo info = api.createSession(recipe);            // 未注册模式/坏组件 → 响亮抛(装配期问题,启动就该炸)
        for (UUID u : participants) {
            if (api.joinSession(info.sessionId(), u) instanceof JoinResult.Rejected rej) {
                lobby.notifyRejected(u, rej.detail());           // 留在大厅
            } else {
                lobby.leave(u);
            }
        }
    }
}
```

要点:

- **`SessionRecipe.of(modeId, mapId)` 钉图 + 空池**:开局地图由票选唯一决定,不吃"装载序第一张"的自动挑图占位策略(../03 §3.2-A3);同会话续局换图同样显式钉图(§4.4)。
- **join 的拒绝面**:入场裁决(JoinAdmission 端口,ADMIT/REJECT 二值)在 `joinSession` 当场返回;被拒者留在主世界大厅,大厅是天然的"被拒兜底"——不再需要 v1.0 的"在大厅收到提示"切换拒绝码链路。
- **多会话并行是自然形态**:大厅每轮开局一个会话(arena 形态);v1.0 的 rotation 单会话常驻形态降级为"局间续局"策略(§4.4),不再是大厅的承载方式。

### 4.4 不同玩法的会话模式切换流程

**共同不变式(四条,写进 review checklist)**:

1. **玩法内部推进零切换**:炸弹攻防的回合循环(RoundComponent 阶段回跳)、首领战的血线阶段(PhaseComponent.jump)都不触发 `switchMode`——切换只发生在**局与局之间**。
2. **局间去向只有两个**:续局(显式 `switchMode`/`requestSwitch` 到下一场)或散场(回大厅,§4.6);"回大厅"没有切换动词,只有散场链路。
3. **大厅永不为切换目标**:大厅不是模式(§4.1);票选"回大厅"的落点是散场,不是 `switchMode(lobby)`。
4. **无显式去向 = 异常态兜底**:竞技模式 EndGate 若没给 intent,框架回落 `session.fallback-mode`(SHDF 不改默认 = 出厂空模式 **limbo**,../31)。宿主把 `ModeSwitchCompleted(to=limbo)` 监听为**待散信号**,触发散场引导(下述"散场"路径)——limbo 不承载任何玩法。

**会话流程策略(SessionFlowPolicy;`games/<玩法>/game.yml` 的 `session-flow` 键,宿主词汇)**:

| 策略 | 一场会话的形状 | 局末动作 | recipe extras(宿主会话组件,随每次 createSession 贡献) |
|---|---|---|---|
| **arena(单场场)** | 一会话一局:开局 → 对局 → MatchEnd → **解散回大厅** | 宿主会话组件 `MatchEndReturn` 引导散场(全员离场)→ `EmptyArenaComponent` 空场收尾解散 | `MatchEndReturn.Spec` + `EmptyArenaComponent.Spec(Duration)` |
| **rotation(循环场)** | 一会话多局:开局 → 对局 → MatchEnd → **局末投票** → 续局 `switchMode`(玩法/地图可变)→ 下一局 → …… 直到票选散场或空场 | 实例内宿主组件(局末投票 + EndGate 显式 intent)产出 `MatchModeSelection` | 局末投票组件 + `EmptyArenaComponent.Spec`(散场收尾) |

**各玩法默认**(均可由 `game.yml` 覆盖):

| 玩法 | 默认流程 | 理由 |
|---|---|---|
| 炸弹攻防(bomb_defusal) | **arena** | 单场局长(多回合),打完一整场玩家流动性大,散场回大厅重新聚合 |
| 团队死斗(team_deathmatch) | **rotation** | 快节奏,同批人连打多图体验最好;局末 15~30s 投票下一场 |
| 首领战(boss_raid) | **arena** | 一场一 Boss,情绪完整闭环;结算展示后散场 |

**局末机制细节**:

- **续局(rotation)**:竞技模式 MatchEnd 阶段挂宿主局末投票组件(原 `VoteComponent` 的局末用法存活,现住宿主包;大厅投票已宿主化,§4.2)。EndGate 的 MatchEnd 判定器产出**显式 intent**:`TransitionIntent(new MatchModeSelection(vote.modeId(), Optional.of(vote.mapId()), false), Handoff.of(战报键, summary))`——同会话切换到下一场。票选"回大厅"时不产 intent,改发宿主自定义实例事件(见下条)。
- **散场(arena 的正常出口,或 rotation 票选回大厅)**:宿主会话组件 `MatchEndReturn`(session 级)消费"局末且无续局"信号(实例自定义事件 `shdf.matchend` 或 `ModeSwitchCompleted(to=limbo)` 兜底),执行**全员离场引导**:逐人 `api.leaveSession(u, LeaveReason.KICK)` + 宿主当场传送回大厅(§4.6;框架 `leave` 不传送玩家,接引责任在宿主);全员离场后 `EmptyArenaComponent`(短窗,如 10s)以 `requestDissolve(DissolveReason.EMPTY)` 收尾,副本世界随解散销毁(../23 REUSE_DIRTY 销毁闭环)。AFK 滞留者由 `MatchEndReturn` 在宽限后强制离场。
  - 公共 API 无解散方法(../07 §7.1)——"对局完成"的解散语义由**空场**承载(人走场散);不为它新增框架口子。若运维需要强散,走框架命令(`ADMIN`)。
- **切换防护照常适用**:续局 `switchMode` 受最短驻留约束(局与局之间天然间隔 MatchEnd 展示,通常已满;不满则票选结果带 `force=false` 被拒时由宿主重试——实测脚本不得绕过防护,§14.16)。

### 4.5 玩法配置与地图装配:宿主自解析 → MapDefinition

**总原则:框架只收 `MapDefinition` 三字段;玩法参数与地图词料全部宿主自解析自持有。**

**配置目录树(宿主数据目录 `plugins/SHDF/`)**:

```
plugins/SHDF/
├── config.yml                      # 大厅:lobby.bounds / lobby.spawn / lobby.vote-seconds / lobby.min-players…
├── games/
│   ├── rotation.yml                # 零票兜底轮换序(v1.0 modes/lobby.yml rotation 键的宿主化)
│   ├── bomb_defusal/
│   │   ├── game.yml                # 该玩法的玩法参数 + session-flow(§4.4)
│   │   └── maps/
│   │       └── crossfire/
│   │           └── map.yml         # crossfire 的**炸弹攻防视角**词料(出生点分组/炸弹点/交互点)
│   ├── team_deathmatch/
│   │   ├── game.yml
│   │   └── maps/
│   │       └── crossfire/map.yml   # 同一张 crossfire 的 TDM 视角词料(队伍出生点/边界)
│   └── boss_raid/…
└── worlds/                         # 世界仓库:一图一目录,全局唯一(与玩法解耦)
```

**两份配置的分工**:

| 文件 | 内容 | 消费者 |
|---|---|---|
| `games/<玩法>/game.yml` | 玩法参数(v1.0 `modes/<id>.yml` 的宿主化:平衡数值/阶段时长/RolePolicy 入参)+ `session-flow` | 宿主工厂**闭包注入**(`registerMode` 时 new 工厂把解析结果喂进去;`build(MatchModeConfig cfg)` 的框架 cfg 形参不经宿主使用——框架 `modes/<id>.yml` 通道对宿主模式缺省为空 config,§15.2 铁律 1) |
| `games/<玩法>/maps/<图>/map.yml` | 该玩法视角的地图词料:出生点分组/区域/交互点(v1.0 `maps/*.yml` 的 spawns/regions/interact-points 块拆玩法各自持有) | 宿主玩法组件,经 `MapDefinition.metadata` 的玩法命名空间 Key 读(下述) |

**`games/bomb_defusal/maps/crossfire/map.yml` 示例**(取代 v1.0 `maps/crossfire.yml`):

```yaml
map-version: 1

tags: [bomb, indoor]             # 并入 MapDefinition TAGS;多玩法共用世界时取并集
reset-strategy: TEMPLATE_RESTORE # ★ 与其它玩法对同图声明不一致 → 启动响亮拒(配置错误)
spawns:                          # 本玩法的出生点分组(宿主词料,不进框架字段)
  attacker: [ { x: 10, y: 64, z: -100, yaw: 0 } ]
  defender: [ { x: -10, y: 64, z: 100, yaw: 180 } ]
bomb-sites:
  site_a: { min: [-10, 60, -30], max: [-2, 70, -22] }
interact-points:
  plant_a: { pos: [-6, 61, -26], radius: 3.0, site: site_a }
```

**装配管线(启动/重载时,一次跑完)**:

```java
package com.shdf.map;   // 宿主地图装配器:games/*/maps/* 自解析 → MapDefinition → registerMap

final class ShdfMapAssembler {

    /** 装配:扫描 → 按世界目录去重 → 词料合并 → 构造三字段声明 → 注册(顺序即铁律 14.39)。 */
    void registerAll(Plugin plugin, MiniGameApi api) {
        Map<String, MapAssembly> byWorld = scanGamesDir();     // world 名 → 各玩法 map.yml 解析结果
        for (MapAssembly m : byWorld.values()) {
            Path worldDir = worldsDir.resolve(m.worldName());
            if (!Files.isDirectory(worldDir)) throw bootFail("世界目录未落盘: " + worldDir);
            AttributeBag.Builder bag = AttributeBag.builder()
                    .put(MapDefinition.TAGS, m.unionTags());   // 框架唯一解释的键(../29)
            m.perGameplay().forEach((gameId, data) ->
                    bag.put(ShdfMapKeys.of(gameId), data));    // 宿主词料:玩法命名空间 Key,同袋共存
            api.registerMap(plugin, new MapDefinition(worldDir, m.resetStrategy(), bag.build()));
        }
    }
}

/** 宿主词料键(住 ShdfMapKeys):一玩法一 Key,值为该玩法的已解析地图数据(不可变 record,如 BombMapData)。 */
AttributeBag.Key<BombMapData> BOMB_MAP_DATA = AttributeBag.Key.of("shdf.bomb.map", BombMapData.class);
```

规则与要点:

- **id = 世界目录名**(框架口径,../26);一图一目录天然全局查重。`games/<玩法>/maps/<图>/map.yml` 的 `world:` 键把玩法词料挂到世界声明上——**同一物理世界服务多玩法**(如 crossfire 同时打 bomb 与 tdm)时,词料按玩法命名空间并存、tags 取并集、`reset-strategy` 必须一致。
- **注册前置**:世界目录**先落盘**(服主把世界放进 `worlds/`;或宿主从打包模板解出)→ 构造 `MapDefinition` → `registerMap`(框架校验路径存在 + 查重,异常文案带绝对路径)。
- **玩法组件读词料**:宿主组件的 `checkMap`/`awake` 从实例地图视图按自家 Key 读:`metadata.get(BOMB_MAP_DATA)`——`checkMap` 缺词料即拒切(v1.0 `map.spawns("boss")` 旧口径的现行形态;../28 起 map/ 包的 SpawnPoint/NamedRegion 等已删,词料归宿主)。
- **热重载** = `unregisterMap`(正被会话使用会被框架拒摘)+ 重新 `registerMap`(../22-D4);玩法参数 `game.yml` 热重载只影响此后 `registerMode` 的新工厂——模式聚合根 build 后不可变(A9),参数热更 = 摘注册重注册(带回退编排,需无存活会话使用该模式)。

### 4.6 散场接引与回大厅

框架送"回家"(主世界出生点),宿主接"回大厅"——两段传送,责任分明:

| 场景 | 框架行为 | 宿主行为(LobbyReturn) |
|---|---|---|
| 对局解散(Dissolved) | 名册成员 hubRelocator → **主世界出生点**;地图世界遗留人员清场传送(../27);副本销毁 | 订阅 `SessionEventView.Dissolved` → 对刚解散成员**接引传送**至大厅 spawn + 恢复大厅态(账本/投票板/清单) |
| 单人中途离场(主动 `/shdf leave`/宿主踢出) | `leaveSession(KICK)` 只动名册,**不传送**(框架现状) | 订阅 `MemberLeft` → 传送该玩家回大厅 |
| 断线(QUIT) | `MemberLeft(reason=QUIT)` **当即发出**(只标记宽限,不移除);宽限内重连恢复(MemberReconnected);宽限满移除**不发事件** | QUIT 时玩家离线,不传送;宽限内重连由框架恢复会话;宽限满被静默移除的玩家下次进服时由宿主(PlayerJoinEvent 自查"不在大厅、不在任何会话")接回大厅 |
| 对局结束散场引导(§4.4) | `MatchEndReturn` 逐人 `leaveSession(KICK)` | 同"单人中途离场"路径:当场传送回大厅 |

```java
package com.shdf.lobby;

/** 解散/离场接引:唯一订阅会话事件的地方(§4.3 开局单闸的镜像——散场单闸)。onDisable 必须 close 订阅句柄。 */
final class LobbyReturnListener implements Consumer<SessionEventView> {

    private final MiniGameApi api;
    private final LobbyManager lobby;
    private EventSubscription subscription;    // onEnable subscribe;onDisable close(幂等)

    @Override public void accept(SessionEventView ev) {
        switch (ev) {
            // 解散时名册已被框架传至主世界出生点(先传后发):此处只做接引收尾——
            // 按"散场引导名单 + MemberLeft 记录"传送回大厅并恢复大厅态(§4.6 时序差要点)。
            case SessionEventView.Dissolved d -> lobby.receiveAllBack(d.session());
            case SessionEventView.MemberLeft m -> lobby.receiveBack(m.player());   // 单人离场:传送回大厅
            case SessionEventView.ModeSwitchCompleted s when "limbo".equals(s.to())
                    -> lobby.signalDraining(s.session());     // 待散信号(§4.4 不变式④)
            default -> { }
        }
    }
}
```

要点:

- **解散时序差**:框架在解散编排内**先传送后发事件**(名册成员先走 hubRelocator,再摘会话、发 `Dissolved`)——宿主接引不依赖 Dissolved 携带名册,以自己散场前的引导名单 + 传送后位置(主世界)兜底;两段传送(出生点→大厅)对玩家是一次无缝衔接,大厅 spawn 与主世界出生点的距离由服主在建服时决定(设成同点则零接引成本)。
- **大厅恢复**:玩家回大厅后重新进入 §4.2 的投票/准备循环——"回大厅"的完整语义 = 位置回区域 + 账本回大厅,与框架状态无关。
